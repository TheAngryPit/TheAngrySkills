### Autopilot-full

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and the root verifies what lands.**

A verdict covers one patch. Green CI covers one head. Step 4 runs a full independent review once at the code-ready head, and again only for new behavior, a redesign, or a large new diff. A minor fix or rebase gets the smallest fresh verification that covers the changed patch. Every new head needs green CI.

1. **Respect the operator's gates.** Items the operator names as theirs and PRs outside the authorized queue stop at merge-ready for the operator. A request to state the plan is not a go. Never merge a PR or bypass a forge approval without authority that covers that action.
2. **Assign one owner per PR and preserve a recovery trail.** Resolve the forge once. Use `gh` by default; use `origin pr` only when the installed `origin` command can resolve this repository. Never require Graphite. Each PR has one native bounded owner with an explicit file and task scope. The owner builds the change, opens its PR early and ready, proves it on the real artifact, runs the repository's checks, and drives it through review and merge readiness. Before the first push, record decisions and child-agent IDs, states, and expected runtimes in the local trail required by `show-me-your-work`. Keep that trail uncommitted. Push after each verified unit. Before every push, run the checks required by the repository's `AGENTS.md` and rules on the committed head. A hook pass is not proof. Finish `cursor-deslop` and `cursor-no-comments` when installed and applicable before reporting the code-ready head. Rebase onto current trunk before code-ready. After that, keep the merge base through fix rounds unless trunk conflicts or breaks CI; rebase again during merge preparation or when a trunk change affects the patch. Report every changed head SHA. Use `--force-with-lease` only for the owner's own branch after checking the remote SHA; never force-push a shared branch.
3. **Run independent owners in parallel from trunk.** Do not stack independent PRs. Give each PR one writer and one branch. Serialize only changes that genuinely overlap. A short private base branch is allowed only when a dependent change must be split.
4. **Verify each review round independently.** At the code-ready head, run independent review lanes that cover the repository gates, the real load-bearing behavior, and the diff. Include a regression comparison against current trunk; if trunk lacks the feature, verify the added behavior and the end state instead. The live lane is mandatory when the surface can be exercised; if no authorized native driver or matching surface is available, state the precise gap and do not claim parity. The author cannot verify their own patch. Audit the receipts at the reported head before issuing one root verdict. Send every proven behavior finding back to the owner with a regression test covering each affected site, or a concrete reproduction receipt when a test cannot show it. A new behavior or large patch change needs a fresh full review. A minor fix, rebase, or conflict resolution needs focused fresh verification for the changed surface. Reuse a prior lane only when the patch-id and its proof conditions still match `playbooks/shipping.md`.
5. **Prepare and merge one PR at a time.** The owner may merge only after the root gives a clean verdict, the current head has green CI, and all required forge checks pass. Rebase onto current trunk immediately before merging, then report the new head and wait for its CI. Check that the merge tree is clean and that trunk changes affecting the PR or its CI have been tested. If a conflict or relevant trunk change exists, rebase or test the merge result and repeat verification as needed. If a third rebase would be needed after merge preparation, stop and report the collision. Squash-merge through the resolved forge and read the PR back to confirm it is merged with trunk as its base. A queued or requested auto-merge is not a completed merge. Only after that readback may a fresh owner take the next authorized item.
6. **Keep approval boundaries and program state visible.** A new increase to a pinned gate or budget requires fresh verifier evidence and a root countersign. A standing operator grant may supply that authorization only when its scope covers the change. Never bypass a forge-enforced approval. Probe delegated owners by their side effects, such as commits, pushes, PR or check changes, and trail updates. If an owner errors, cannot start, or exceeds its established runtime without a new side effect, mark it stuck and replace it when its work remains needed. A wait for the operator is not a stall. Use a native Codex heartbeat for recurring audits only when the operator explicitly requests recurring monitoring and the task environment supports it. Otherwise report the cadence gap; do not substitute a lossy notification or an unrequested loop.
7. **Stand down on the operator's hold.** A hold reaches every owner as a zero-write instruction. Each reports its state and preserves its brief until the operator releases it.

**Reply:** report each PR's state and head, independent verdict and author, CI and merge readback, what merged, approval countersigns and reasons, and every open operator gate. Link the PRs and local trails.
